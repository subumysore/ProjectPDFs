# ADR-0020 — Distribution trust WITHOUT a paid code-signing certificate

- Status: Accepted
- Date: 2026-07-23
- Supersedes: nothing. Amends the distribution half of ADR-0002 (native stack) and the release
  guidance in `docs/reference/code-signing.md`.

## Context

Shipping 1.0.0 GA is blocked on exactly one thing: a Windows Authenticode certificate. An OV or EV
certificate costs money **and** requires organisation identity validation by a CA — neither of which
can be automated, and neither of which is available to this project right now. Revenue has to come
first.

Facts that constrain the decision:

- **Distributing unsigned software is entirely legal.** Authenticode is a trust-and-reputation
  system, not a licence to distribute. There is no legal, contractual, or platform-policy barrier to
  publishing an unsigned Windows installer.
- **A self-signed certificate does not help a public download.** Its root is trusted only on the
  machine that created it. On every other machine the chain does not validate, so SmartScreen shows
  the identical "unknown publisher" wall it shows for an unsigned binary. It buys nothing — and it is
  strictly *worse* under some enterprise/AV policies, which treat *"signature present but chain
  invalid"* more harshly than *"no signature at all"*, because an invalid chain looks like tampering.
- **SmartScreen's warning is driven by download reputation, not merely by signature.** Reputation
  accrues to a (publisher, binary) pair through download volume. An OV certificate does not remove
  the warning on day one either — it only lets reputation *accumulate against a stable identity*.
  Only EV grants instant trust.
- **The browser-download path is what triggers the warning.** A file downloaded by a browser is
  tagged with the Mark-of-the-Web, which is what invokes the SmartScreen check on launch.
- **The extension has no equivalent problem.** The Chrome Web Store charges a one-time $5 developer
  registration fee and Web Store installs never touch SmartScreen.
- **winget does not require code signing.** The community repository accepts unsigned `.exe` and
  `.msi` installers; signature checks run during validation but are non-blocking. **MSIX is the
  exception** — App Installer requires MSIX packages to be signed with a commercially obtained
  certificate.

## Decision

Treat "no certificate" as a **presentation and distribution-channel problem**, not a blocker, and
solve it with four moves that cost nothing and are not thrown away when a certificate is eventually
bought.

1. **Do NOT sign public releases with a self-signed certificate.** Self-signing stays strictly a
   dev-only tool for exercising the pipeline (`scripts/new-dev-signing-cert.ps1`). Public artifacts
   ship honestly unsigned rather than carrying a signature that cannot validate. `sign-windows.ps1`
   already no-ops safely when no cert env var is set, so this is the default behaviour — we simply
   stop treating self-signing as a shipping option.

2. **Make the browser extension the primary install path.** It is the cheapest ($5, one-time), the
   fastest to install, has zero SmartScreen friction, and already delivers the core product. The
   desktop app is presented as the optional power-user companion, not the front door.

3. **Add winget as the recommended desktop install channel.** `winget install PolyglotFormFill`
   requires no certificate, and the resulting install is not a browser download, so the Mark-of-the-Web
   reputation prompt does not gate it. Stay on our existing NSIS `.exe` / `.msi` bundles; **do not
   move to MSIX**, which would reintroduce the paid-certificate requirement we are avoiding.

4. **Publish verifiable release integrity, and set expectations honestly and calmly.**
   - Every release artifact gets a published **SHA-256** in a machine-readable manifest generated by
     `scripts/release-manifest.mjs`, with a one-line verification command a user can run.
   - The install page **predicts the SmartScreen warning before the user clicks download**, shows
     what it looks like, explains in one sentence why it appears, and gives the exact click path.
     A warning the user was told to expect reads as competence; the same warning unannounced reads
     as danger. This is the single highest-leverage, zero-cost move for not scaring users.
   - Framing rule: never apologise, never use alarm words, never imply the user is taking a risk they
     are not. State the cause (no certificate purchased yet), the proof offered instead (hash), and
     the path forward. See `docs/specs/release-integrity.md` for the binding copy rules.

**Upgrade path (why this is future-proof).** Nothing above is discarded when a certificate is bought.
Signing is a one-line change — set `WINDOWS_CERT_THUMBPRINT` and rebuild; the hook, timestamping and
verification are already built and exercised. The hash manifest remains valuable regardless (it is
the integrity story that signing does not replace). winget remains the preferred channel. The install
page's expectation-setting block is deleted, and nothing else changes. Preferred first purchase is
**OV** — cheaper, and reputation accrues from the moment a stable publisher identity exists.

## Consequences

- **GA is no longer blocked on a purchase.** The remaining desktop friction is one extra click on
  first install, disclosed in advance.
- Users who download via the browser still see the SmartScreen prompt. We accept this, disclosed.
- Some corporate environments block unsigned installers outright by policy. Those users are directed
  to the extension, which is unaffected. This is a real, named limitation, not a papered-over one.
- We carry an ongoing honesty obligation: the install page must state the build is unsigned. Removing
  that statement is only permitted once a real CA certificate is actually in use.
- winget submission adds a release step (manifest PR per version, with the SHA-256 the manifest
  generator already produces — the same hash serves both purposes).

## Alternatives considered

- **Self-sign public releases** — rejected: no SmartScreen benefit, and an invalid chain is worse
  than no signature under some policies.
- **MSIX packaging** — rejected: requires a commercially obtained certificate, i.e. the exact cost
  being avoided.
- **SignPath.io free OSS tier** — genuinely free certificate-backed signing, but conditional on the
  project being open source. Left open as a real option should the licensing model change; it is not
  assumed here.
- **Delay GA until a certificate is affordable** — rejected: revenue must precede the purchase, so
  this is circular.
- **Ship without disclosing the warning** — rejected: an unexpected security warning is precisely
  what frightens users and destroys trust in a privacy product.
